# FreshEye 最终封板设计规范

## 1. 目标

在保持 FreshEye 现有深海蓝与青绿色品牌语言、Vue 3 + TypeScript 架构、公开页面 URL、模型选择和 FastAPI 接口不变的前提下，完成一次可作为最终版本发布的封板升级：

- 收敛 UI 层级、控件状态、动画策略、代码边界、注释与错误处理。
- 完整覆盖键盘、触控、鼠标、减少动态效果、焦点恢复和屏幕阅读器语义。
- 深度适配手机竖屏、手机横屏、平板、常规桌面、宽屏桌面和文本放大场景。
- 重新验证中英文页面、动态识别结果、历史记录、相机和单页 A4 PDF 报告。
- 将自动化测试纳入 GitHub Pages 部署门禁，最终直接推送 `main`，不创建 PR。

## 2. 当前基线与主要缺口

基线审计以提交 `019b73a` 为准：前端契约测试 22 项通过，TypeScript 检查通过；1440、768 和 390 像素真实 Chromium 视口没有横向溢出，现有视觉方向完整且无需重做。

封板仍需解决以下问题：

1. `HomeView.vue` 同时承担媒体流、上传、分析、结果呈现、历史记录和多个弹窗，生命周期职责过于集中。
2. 新手引导和低置信度弹窗缺少完整的 dialog 语义、Esc 关闭、焦点约束、页面滚动锁定和关闭后的焦点恢复。
3. API 与历史记录各自维护一套预测字段标准化规则，容易出现空值、百分比和历史兼容行为漂移。
4. 移动菜单没有在路由变化或视口由移动端切换到桌面端时统一收口；路由切换后也没有明确的页面焦点落点。
5. 动画只在首次挂载时读取减少动态效果偏好，没有处理偏好动态变化、页面进入后台和粗指针设备。
6. 现有测试主要检查源码契约，尚不能作为弹窗、导航、响应式和语言切换的运行时证据。
7. 少量注释已经与当前实现不一致；部分错误回退静默失败，无法给用户明确的恢复路径。

## 3. 设计原则

### 3.1 保持产品边界

- 不改变 `/`、`/guide.html`、`/fish.html`、`/about.html` 和 `/404.html`。
- 不改变 `POST /predict_with_gradcam?model_version=v1|v2`、multipart 字段 `file` 或返回字段。
- 不重做页面内容结构，不增加账号、云历史、后端数据或新的模型能力。
- 不引入第二套 UI 主题；现有深海品牌设计作为唯一视觉系统继续精修。

### 3.2 只拆分生命周期复杂度

采用针对性组件化，不进行全面首页重写：

- 新增共享 `AccessibleDialog.vue`，统一普通模态框的语义、焦点约束、Esc、遮罩关闭、滚动锁定和焦点恢复。
- 将相机界面与媒体流生命周期收敛到 `CameraCaptureDialog.vue`；组件只接收打开状态和文案，向首页发送 `capture`、`close` 与回退选择事件。
- 新增纯函数模块 `utils/prediction.ts`，统一概率、标签、置信度和模型字段标准化；API 与历史记录共同使用。
- `HomeView.vue` 继续负责编排上传 → 分析 → 结果 → 历史流程，避免通过大量 props 和事件拆散同一业务状态。

组件边界必须满足：关闭相机一定停止全部轨道；关闭任意模态框一定恢复原焦点和页面滚动；历史兼容和实时 API 使用同一套概率语义。

## 4. UI 与交互封板

### 4.1 控件状态

- 按钮、链接、选择框、标签页、手风琴和可拖动热力图统一具备默认、悬停、按下、键盘焦点、禁用、忙碌和错误状态。
- 悬停位移只应用于支持 hover 的精细指针设备，触控端不保留粘滞 hover。
- 所有主要按钮保持至少 44 × 44 CSS 像素触控区域；危险操作继续使用二次确认。
- 分析、样例加载、相机启动和 PDF 生成期间暴露 `aria-busy` 或可感知状态，阻止重复提交。

### 4.2 模态框与导航

- 普通模态框使用 `role="dialog"`、`aria-modal="true"`、标题关联和说明关联。
- 打开时记录触发元素并聚焦首个合理控件；Tab/Shift+Tab 在框内循环；Esc 关闭；关闭后恢复焦点。
- 模态框打开期间锁定正文滚动，嵌套或连续弹窗不会错误覆盖原始 `body` 样式。
- 移动菜单在路由变化、Escape、点击链接、视口进入桌面断点或组件卸载时关闭并恢复页面状态。
- 路由切换后，正常导航将焦点移动到主内容容器；浏览器前进/后退保留滚动恢复语义。

### 4.3 错误恢复

- 图片读取、压缩、相机权限、媒体轨道、网络、超时、限流、服务冷启动和弹窗阻止分别给出可操作提示。
- 图片预处理失败时不进入不可分析的半完成预览态；用户可重新选择、使用原图重试或返回上传入口。
- 分析请求只允许当前任务更新结果，后到达的旧请求不能覆盖新文件或新模型的结果。
- 所有 object URL、媒体轨道、定时器、监听器和临时下载 URL 在关闭、替换或卸载时释放。

## 5. 动画与性能策略

- 建立统一的运动偏好状态，监听 `prefers-reduced-motion` 的实时变化。
- 页面不可见时暂停装饰性漂移、计数动画和不必要的循环更新；恢复可见时安全继续或保持最终值。
- 粗指针/无 hover 设备禁用鼠标跟随与高成本悬停动画，但保留信息层级和明确的按下反馈。
- reveal 动画只观察待展示节点，不再为每次无关 DOM 变化全量扫描页面；节点进入视口后立即解除观察。
- 路由、弹窗和手风琴动画使用统一时长 token；减少动态效果下立即显示最终状态。
- 任何动画都不能阻止点击、焦点、滚动或 PDF 内容测量。

## 6. 响应式与浏览器适配矩阵

### 6.1 视口

必须验证：

- 320 × 568：窄屏手机下限。
- 360 × 800、390 × 844、430 × 932：常见手机竖屏。
- 844 × 390：手机横屏和短视口。
- 768 × 1024、1024 × 768：平板竖屏与横屏。
- 1280 × 720、1440 × 900、1920 × 1080：桌面与宽屏。

### 6.2 适配规则

- 不允许正文横向溢出、固定宽度裁切、弹窗超出安全区或底部操作被浏览器工具栏遮挡。
- 使用 `svh`/`dvh`、safe-area inset 和短视口滚动回退处理移动浏览器动态工具栏。
- 手机横屏下相机、菜单和普通模态框允许内部滚动，主操作始终可达。
- 表格、结果标签页、概率图、热力图、历史卡片和 PDF 操作在窄屏下保持可读，不通过缩小到不可点击来适配。
- 200% 文本缩放下核心流程仍可操作，不依赖单行标题或固定高度。
- 以 Chromium/Chrome 和 Edge 做真实运行验证；对 Safari/iOS 与 Firefox 使用标准能力、CSS 回退和静态兼容审查，不能依赖 Chromium 专属行为。

## 7. 中英文与 PDF

- 中文和英文语言包必须具有相同的键和数据形状，移除不安全的强制类型断言。
- 英文按钮、状态、帮助、错误和模型说明按产品界面语气复核，避免直译、过长标题和中英文标点混用。
- 语言切换后更新文档标题、描述、`html[lang]`、当前弹窗、动态结果、历史相对时间和报告文案。
- PDF 继续采用独立、无外部字体依赖的单页 A4 输出，不修改后端数据。
- 中文与英文分别验证高度新鲜、新鲜、不新鲜及长文本边界；模型、置信度、概率顺序、时间、页脚、免责声明、原图和热力图必须准确。
- 打印控件不进入报告正文；报告弹窗被拦截时保留明确提示，不静默失败。

## 8. 测试与发布门禁

### 8.1 测试层次

1. 现有 Node 契约测试继续验证路由、资源、开源清单和关键静态约束。
2. 增加可执行的单元测试，覆盖预测标准化、语言包形状和错误映射。
3. 增加轻量 Playwright 封板测试，覆盖：
   - 五个公开入口直达与中英文切换；
   - 移动菜单、路由焦点、模态框焦点循环和 Esc；
   - 上传、样例、模拟 API 结果、标签页、手风琴、热力图、历史记录；
   - 相机权限失败与流清理；
   - 多视口无溢出、减少动态效果和短视口；
   - 中英文 PDF 预览内容与单页打印布局。
4. GitHub Pages workflow 在构建和部署前运行前端测试；任何测试或构建失败均不得发布。

### 8.2 最终验收证据

- `npm test`、运行时单元测试、Playwright、`npm run typecheck`、`npm run build` 全部以零失败退出。
- FastAPI 测试覆盖健康检查、V1/V2、Grad-CAM、格式、尺寸、缓存、限流和 CORS。
- `git diff --check`、跟踪文件扫描、敏感信息扫描、忽略规则和构建产物检查通过。
- 中文与英文 PDF 均渲染为一页 A4，并完成截图与文本提取复核。
- 推送后确认 GitHub `main`、本地 `HEAD` 和远端引用为同一提交；Pages workflow 成功后对正式域名完成桌面与移动端 smoke test。

## 10. 完成定义

只有以下条件同时成立才可称为“最终封板”：

1. 设计、动画、代码逻辑、注释和交互缺口均有对应实现与测试证据。
2. 所有目标视口、输入方式、语言、关键异常和 PDF 报告通过验收。
3. 深度代码审查没有未解决的关键或重要问题。
4. 仓库不包含临时截图、生成报告、缓存、构建产物、凭据或无关文件。
5. 最终提交已直接推送 `origin/main`，GitHub Pages 部署成功，正式站点 smoke test 通过。
